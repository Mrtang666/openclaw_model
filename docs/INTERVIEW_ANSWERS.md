# OpenClaw 面试参考答案

> 与 [INTERVIEW_QUESTIONS.md](INTERVIEW_QUESTIONS.md) 的 1-160 题逐题对应。以下是基于当前仓库的推荐答法，不是要求逐字背诵。应优先陈述“当前已经实现”，再补充“生产化时我会怎样完善”；不要把后一部分说成已经上线的能力。

## 1. 项目全景、价值与真实性（1-10）

1. OpenClaw 是一个模块化单体智能助手：以 CLI 和微信为入口，将对话、工具调用、记忆/RAG、多模态处理串成任务闭环；另外包含医疗照护协同和小红书舆情两个垂直工作台。目标不是做一个只会聊天的机器人，而是让受控工具真正完成查询、提醒、文档和协同任务。
2. CLI 适合运维和本地操作，微信是面向普通用户的主入口；医疗控制台和小红书控制台面向不同业务人员。通用层是配置、数据库、工具协议、模型与通知能力；医疗和舆情的领域模型、权限与工作流应保持隔离。
3. 简历可写为：“基于 Spring Boot 构建的多通道 Agent 平台，支持微信多连接、Function Calling、RAG、受控工具及医疗/舆情工作流。”不应写成“已大规模分布式生产系统”。
4. 应选一个自己真正负责的闭环，例如微信 Agent Loop：需求是让模型能多步调用工具；核心是结构化 tool-call 协议、参数校验、循环上限与结果回写；测试应覆盖正常调用、参数错误、超时和重复副作用。
5. 微信 iLink、DashScope、Qdrant、地图天气、邮件、网盘、Sidecar 都是外部依赖。当前合理策略是把调用包装在 client/adapter 中，缺失配置时关闭可选能力并明确提示；不能假称所有能力在依赖故障时仍然可用。
6. 难点可概括为：多轮工具调用的协议正确性、同一会话的消息顺序、跨域数据的权限与审计。代价是代码里存在较多工具和配置，需要以测试、观测与模块边界控制复杂度。
7. 已闭环的重点是工具注册、微信会话、RAG、提醒、医疗/舆情的数据库与服务层。外部平台真实可用性依赖账户、密钥、Sidecar 与部署环境，因此现场应说明配置前提。
8. 演示建议选三条：微信“查信息并生成语音”的多工具链；患者授权后的照护计划/任务闭环；小红书采集到风险事件、报表和投递。它们能展示状态、权限、异步任务，而不只是 LLM 文本。
9. 最大债务是单机内存状态和跨资源最终一致性尚未完全生产化。优先补请求链路观测、幂等/outbox、关键权限测试和迁移发布策略，再考虑拆服务。
10. 可用性用端到端成功率、P95 延迟、工具失败/重试率、队列拒绝率、RAG 引用忠实度、告警人工确认率和单任务 Token/外部调用成本衡量；当前项目应先建立这些基线，不能凭一次演示下结论。

## 2. 架构与技术选型（11-22）

11. Java/Spring Boot 适合承载长生命周期服务、依赖注入、调度、事务和类型化业务；Python 放在小红书采集 Sidecar 是因为其爬取生态和运行时隔离更合适。语言选择服务于边界，而不是追求统一语言。
12. Spring JDBC 让 SQL、迁移和条件更新显式可控，适合当前以仓储接口封装的项目；代价是映射和事务边界需要开发者更自律。复杂聚合增长后可评估 MyBatis，但不应为了 ORM 而重写稳定查询。
13. 主 JVM 负责微信、Agent、领域服务和 API；MySQL 存业务事实，Qdrant 存向量；Python Sidecar 采集小红书，Node Sidecar 执行浏览器 MCP；模型和第三方 API 都是边界外服务。组件图应明确主服务是唯一决策与鉴权方。
14. adapter 隔离 SDK，client 封装 HTTP，repository 操作持久化，service 编排领域规则，tool 把受控能力暴露给 Agent，controller 提供 HTTP。若 controller 直接拼 SQL 或工具直接绕过权限服务，就是应收敛的越层。
15. `WechatTool` 把能力以统一 schema、执行结果和注册方式交给模型，便于新增、测试、审计和按风险分级；把分支堆在会话服务会使编排类变成 God Class，也无法统一校验与超时。
16. CLI 与微信的交互、身份和回复媒介不同，所以入口流程可不同；模型调用、工具 schema、执行结果、错误分类可逐步复用。不要强行抽象出掩盖两端语义的大接口。
17. 保留两种模式是为了兼容模型能力和回归比较。应按会话灰度、记录工具成功率/轮数/成本，确保 Function Calling 的稳定性和覆盖率达到门槛后再删除旧模式。
18. 外部能力应通过配置开关和 Noop/明确失败实现降级，Bean 创建不能在启动时强制联网。基础会话、CLI、数据库等核心能力与可选媒体/采集能力要分开。
19. 外部 DTO 应在 adapter/client 内转换为领域对象，避免 SDK 字段渗透到 service。协议变化时只修改边界适配层并补契约测试，减少业务层连锁修改。
20. 先保持模块化单体；当连接处理、采集、报表/媒体出现独立扩缩容、不同发布频率或故障互相影响时再拆。先拆 Sidecar 这类天然独立运行时，比过早拆核心会话更合理。
21. 多实例后，连接 ownership、登录 session、mailbox、内存确认 token、本地文件和本地调度都不可靠。它们要外置到持久存储/消息队列，或通过一致性哈希固定会话归属。
22. 非敏感默认值放 properties，环境差异和密钥走环境变量/密钥系统，`.env` 仅用于本地且不提交。配置必须有启动校验、脱敏日志和环境清单，避免开发与生产漂移。

## 3. 微信通道、多连接与消息生命周期（23-32）

23. 当前链路应说明为：`WechatBotService` 接收 SDK 消息，分发器按会话串行化，`WechatConversationService` 组装上下文和 RAG，`FunctionCallingAgentLoop` 调模型/工具，回复持久化并由微信 client 发送。每段都应有错误转换和 trace 标识。
24. 文本直接进入编排；图片/语音/视频/文件先经输入解析、存储或识别，得到可引用的上下文，再与文本合并进入 Agent。最终 `WechatReply.parts` 统一承载文字、媒体与文件。
25. `connectionId` 区分哪个微信登录连接，`userId` 是该连接下的聊天对象，`botId` 可表示机器人配置或身份。仅用 userId 会让不同微信账号中同名/同 ID 会话串线。
26. 多连接由 bot 管理器与 `WechatBotService` 生命周期管理。创建同一连接应使用状态机和原子占位/唯一约束，只有一个请求能从“未启动”进入“登录中”。
27. 限额应在申请连接前连同“登录中”状态计入，否则并发扫码可绕开上限。多节点时须使用数据库条件插入或分布式计数，内存计数只适用于当前单机。
28. 断线后可根据 SDK 能力做受限重连；凭据和扫码 session 若仅在内存，进程重启通常需重新登录。重连必须与消息去重、发送状态配合，不能盲重发。
29. 回调应按至少一次来处理，理想去重键为渠道消息 ID 加 connectionId，并持久化收件记录。若 SDK 无稳定 ID，可退化为发送方、时间窗与内容摘要，但会有误判，必须说明局限。
30. “正在处理”降低长任务的无反馈感；终态必须发送成功、失败或稍后重试的说明，并把状态写入可查询记录。否则用户会只看到悬空提示。
31. 回复 part 的顺序应由 Agent/工具结果的显式顺序决定，发送层按该顺序投递并记录每 part 状态。失败时只重试未发送 part，并避免对有副作用的媒体/文件重复创建。
32. 登录管理页面在生产需后台身份认证、HTTPS、CSRF 防护、短期 session 与最小权限；二维码和登录 token 不能被缓存、日志或无授权 API 返回。

## 4. 并发、顺序、背压与分布式可靠性（33-44）

33. `connectionId + userId` mailbox 保证同一会话按到达顺序处理，避免前一轮记忆/工具结果被后一轮覆盖；不同会话仍可并行，从而避免全局串行。
34. ConcurrentMap 保证 mailbox 查找/创建安全，mailbox 内部同步保证单消费者、入队和空闲回收不互相破坏。需要强调实现正确性要由并发测试和状态不变量验证，而不只靠“加锁”。
35. 正确做法是让“判空、标记停止、删除”与新的入队协调：入队若发现已停止则重新激活，消费者删除前再次确认队列为空。否则会出现消息落入已删除 mailbox 或双消费者，需用 race test 验证。
36. 线程池由模型并发额度、下游连接池、平均/峰值耗时和可接受排队时间共同决定，不是按 CPU 核数随意设置。长 IO 任务还应与快速消息任务隔离。
37. 拒绝应在提交处捕获，写指标并回复“系统繁忙，请稍后重试”；不能让异常在 SDK 回调线程静默丢失。生产可增加限流和按会话的排队上限。
38. 100 条连续消息会使同一 mailbox 按序排队，延迟可能失控。应对策略是每会话上限、意图合并、取消过时任务和速率限制；选择要符合聊天语义，不能无声丢用户输入。
39. 同会话串行意味着长工具会阻塞后续消息，这是当前一致性与体验的取舍。改善方案是可取消任务、工具 deadline、异步任务状态和“新消息是否取代旧任务”的产品规则。
40. 背压应从下游限流/连接池反传到工具并发阀、会话队列和入口限频。公平性可通过每会话配额、加权队列、独立线程池或令牌桶保障。
41. 优雅停机先停止接收，再等待有界时间；可重放任务持久化为待处理记录，短暂只读任务可取消。关键点是发送/写库的幂等键，而非保证进程永不终止。
42. 多实例下消息可能落到不同 JVM，进程内 mailbox 无法看到彼此。可用按会话分区的队列消费者、Redis Stream consumer group 或 ownership 锁；分区队列通常比每消息加分布式锁吞吐更稳定。
43. 不能用一个数据库事务包住微信和模型调用，应采用 inbox 去重、业务记录、outbox 投递和状态重试。消息已回库但发送失败时，outbox 可重投；已发送则用渠道/业务幂等键抑制重复。
44. 压测应覆盖多会话和热点单会话，观察端到端延迟、排队时间、队列深度、拒绝数、线程池饱和、DB 池、模型限流、工具错误和内存曲线，并设定容量阈值。

## 5. Function Calling Agent（45-60）

45. system 定义边界，user 提供任务，assistant 可能产出 tool calls，tool 消息返回对应执行结果；`tool_call_id` 使模型知道哪条结果对应哪次调用。错配会导致模型把结果归因给错误动作。
46. assistant tool calls 与所有 tool results 是同一协议回合的一部分，少回写会让模型不知道工具是否执行或缺少并列结果，常见后果是重复调用、编造结果或协议错误。
47. Agent Loop 构建 messages 与可见工具，调用模型；若有 tool calls 则校验、执行、将结果追加后继续；无 tool calls 时把最终文本转为回复。循环还要在上限、超时和不可恢复错误处收敛。
48. `maxLoopRounds=5` 是失控保护而不是业务真理。生产还需总 deadline、每工具调用上限、Token/金额预算和会话级限流，超过后返回已完成部分与明确状态。
49. 当前应先以安全的串行执行为基线；同轮独立只读调用可并行，但依赖关系不能由“同轮顺序”猜测。规划器能表达 DAG 后再并行，副作用操作默认串行并确认。
50. 当前 `previous_result` 可支持线性链，但丢失多分支名称、类型和来源。长远应使用带 key、来源、敏感级别和生命周期的任务工作区，而不是把大段结果注入下一个参数。
51. 重复签名去重只能减少显而易见的循环，不能解决换参、时间相关或模型重试。邮件/订单等工具必须在业务层以请求幂等键和状态机保证一次语义。
52. 幂等键是同一业务意图在重试中保持不变的唯一标识。邮件可用会话+确认 token+内容摘要，提醒用用户+时间+内容，支付/订单依赖外部支付单号；重复请求返回已有结果。
53. Validator 负责统一 schema、必填、类型、枚举与额外字段；工具仍须校验领域权限、资源存在性、状态和业务约束。模型永远是不可信输入。
54. 任意 HTTP 会造成 SSRF、越权和数据外泄。将工具按意图/权限裁剪能减少误选和 prompt 成本，危险工具还需显式确认和白名单目标。
55. 超时、429、5xx 可在有上限的退避后重试；参数/权限错误应立即返回；部分成功要携带已完成项和后续选择。让模型自愈只适用于不产生副作用且错误信息可安全暴露的场景。
56. 空 content 且无 tool call 应当以安全兜底结束并记录模型异常，而不是无限重试。可提示用户重试或降级为基础聊天。
57. 旧 JSON 模式必须有严格解析与错误分类；Function Calling 也要做协议版本契约测试。两种模式的成功率、轮数和工具错误应并列观测，作为迁移依据。
58. Agent trace 应存 prompt/工具版本、脱敏后的输入摘要、每轮调用、工具结果摘要、耗时、Token、错误和关联 ID。密钥、病历、邮件正文、Cookie 与本地路径不应写入可广泛访问日志。
59. Java 常量难以做版本、灰度和回滚。应把 prompt 做成有版本的受控资源，结合固定评测集、灰度标签和线上反馈进行发布。
60. 规划器+执行器可显式管理依赖、确认点、重试和恢复；代价是计划语义、状态持久化和调试复杂度大。当前循环适合短链路，长任务再逐步引入状态机。

## 6. 工具体系、MCP 与外部能力（61-76）

61. 新工具至少要有定义/schema、实现、注册、参数与权限校验、风险/确认策略、超时错误处理、单元测试和使用文档；否则模型可见性与实际能力会漂移。
62. 解决 schema 漂移应让定义生成校验器或让同一个 typed request 同时驱动 schema 与解析；不能维护三份手写字段规则。
63. `Map<String,String>` 对嵌套对象、数组和数值表达不自然，且把类型错误推迟到运行时。应逐步改为 JSON node/DTO 加 JSON Schema 或 bean validation。
64. `modelText` 是给模型继续推理的最小可信事实，`visibleParts` 是给用户的呈现，状态/错误用于编排。凭据、完整邮件、精确医疗隐私和内部路径必须按最小必要原则隔离。
65. 只读工具可短超时有限重试；写入工具需幂等、审计和状态查询；危险操作必须人审/二次确认。所有级别都需速率限制和可观测性，但策略不能一刀切。
66. 地图/天气等结果可能过期、地址歧义或供应商失败，工具应返回来源、时间和置信信息。模型只能说“查询到/建议”，不能把预估路线或商品建议说成交易已完成。
67. 相对与绝对时间分工具可减少模型心算和歧义；服务端要统一时区、保存 ISO 时间和原始表达。夏令时地区需以用户时区库解析，歧义时间要求确认。
68. snooze 必须绑定已投递提醒的 ID、发送时间和内容摘要，必要时列出候选让用户选择。否则“延后一下”会操作错误任务或重复创建。
69. 多实例调度使用条件更新/租约抢占到期任务，把状态改为处理中；投递使用提醒 ID 幂等键并记录尝试。租约超时可接管，但需避免旧 worker 继续发送。
70. 邮件查询、纯文本发送、附件发送风险不同：查询涉及隐私读取，附件涉及文件外泄和更高成本。拆工具可单独配置权限、确认和审计。
71. 非白名单地址的确认 token 应绑定用户、会话、收件人、主题/附件摘要和过期时间，并一次性消费。token 不能只是一段通用随机字符串，否则可被转发重放。
72. 附件需在受控根目录内做 canonical path 校验，限制总大小/数量/MIME，显式排除密钥、Git、日志、构建和依赖目录。目录打包前还应展示文件清单供用户确认。
73. 网盘 token 按用户加密存储、仅在服务端解密使用，支持过期刷新与撤销；所有文件操作必须带用户/授权范围过滤，不能以模型传入的路径作为权限依据。
74. 浏览器 Sidecar 隔离 Node/浏览器依赖和崩溃域，也便于限制权限。风险包括任意 URL、下载内容、登录 cookie、截图隐私和网页中的间接注入。
75. localhost 不能阻挡同机恶意进程或被 SSRF 的本机服务；主服务与 Sidecar 还需共享密钥/签名、请求时限、最小工具集、健康检查和明确的协议版本。
76. 触及下单/支付时浏览器执行器必须停在预览和确认页，展示商户、商品、金额、地址与操作摘要，只有经过绑定确认才可提交。模型不能自行“确认”。

## 7. 记忆、知识库与 RAG（77-88）

77. 最近轮次保留对话细节，摘要压缩长期上下文，偏好保存稳定选择，工具状态支撑跨轮任务，文件归档支持引用，知识库提供外部事实。全部塞进 prompt 会超 Token、泄露隐私且降低检索质量。
78. 流程是导入与解析、按语义切块、生成 embedding、写 Qdrant 和元数据、按用户/权限过滤检索、重排去重、截断证据并注入模型，最终回答附来源或不确定性。任何一步失败都要可追踪与补偿。
79. Qdrant 适合向量相似度和 metadata 过滤；collection、维度和距离必须与 embedding 模型匹配。metadata 至少包含知识 ID、用户/租户、来源、版本和权限范围。
80. 隔离靠服务端查询过滤、资源归属校验和数据库/向量 metadata，而非 prompt。所有取回和下载接口都要再次校验当前身份，防 IDOR。
81. 这是间接 Prompt Injection。把检索文档视为不可信数据，明确隔离指令与内容，禁止文档触发工具，工具调用仍必须经 schema、权限和确认。
82. 查询规划提取检索意图，证据包控制数量和来源，rerank 提升语义相关性。仅 Top-K 容易引入重复块、关键词偏差和超长上下文。
83. 对相互矛盾信息，时间更近的用户原话可作为待确认信号，但医疗事实不能直接覆盖旧记录。回答要说明冲突并要求确认，再按版本化流程更新。
84. 摘要是模型产物，不应自动升级为关键事实；对医疗/高风险偏好采用确认状态和来源。用户应可查看、更正和删除非强制留存的记忆。
85. 内存降级可维持短暂服务，但重启会丢失，恢复后也可能与持久会话分叉。应优先告知降级；若需要写回，使用带顺序与幂等键的重放队列。
86. 优先级建议是当前明确用户指令 > 已验证的领域事实 > 当前会话最近内容 > 可追溯 RAG 证据 > 模型摘要/偏好。冲突不能静默选择，应提示用户或走审核。
87. 评测用标注查询集合测召回/排序，人工或模型裁判测忠实度与引用覆盖，记录无证据断言率、延迟、Token 与检索成本。指标要按业务类型分桶。
88. MySQL 与 Qdrant 无全局事务，应保存导入状态并用 outbox/补偿任务驱动另一侧写入或删除；检索时只使用状态完整的文档，避免孤儿向量暴露。

## 8. 多模态、文档与报告（89-95）

89. 每类媒体都应有受控输入、文件存储键、处理状态、模型/服务调用和可下载输出；识别失败不应阻塞原文件保存。生命周期应包含上传、引用、过期清理和访问授权。
90. 无任务文件先归档到当前用户/会话的待引用集合，并在后续“刚才的文件”中按时间和类型解析。跨用户或跨连接必须用服务端归属过滤。
91. 指代消解先查最近、同会话、同类型候选；不唯一时让用户选择，不要猜测。解析结果应记录实际资源 ID，而非把自然语言一直留到执行时。
92. 同类型替换只适合单一“当前头像/当前结果”语义，不适合多图多附件。更合理的是 reply part/asset 的有序列表和明确的 superseded 标记。
93. 报告链接使用高熵不可预测 ID，下载端再做身份/归属校验，HTML 采用转义/CSP，文件设置 TTL 并由清理任务回收。仅靠隐藏路径不是授权。
94. 报告测试不仅检查字节非空，还要用解析库或渲染器验证可打开、页数/工作表、关键字段、表格和下载响应。对模板变更保留快照测试。
95. 文件名和 MIME 要由服务端白名单决定，存储 key 不接受用户路径，富文本必须消毒和转义，下载设置 `Content-Disposition` 与安全响应头。恶意附件还需病毒扫描或至少隔离策略。

## 9. 医疗照护协同与隐私（96-109）

96. 模型只适合辅助沟通和信息提取，不能替代医疗判断。确定规则识别紧急关键词/指标，低置信号进入人工确认，紧急场景给安全升级建议和通知流程。
97. RBAC 只能表达角色，不能表达“此医生是否被此患者当前授权”。因此需患者-照护者关系、有效期、数据域和操作范围，服务端每次读写都校验。
98. 对话模式只是模型表达约束，真实权限在 controller/service/repository 的身份与授权检查。即使模型被诱导，也不能绕过后端授权。
99. 状态机把“用户原始陈述”“模型提取”“等待确认”“已验证事实”分离。未验证内容不能作为病历事实或高风险决策依据。
100. 计划状态机让草稿、审核、生效、暂停和完成可追踪；服务端拒绝非法跳转，例如未审核直接生效或已完成再次编辑。状态变化应记录操作者和时间。
101. 用 version 列乐观锁或 `where id=? and status=? and version=?` 条件更新；冲突时返回当前版本和差异，要求重新确认。审计记录两个操作而不是静默覆盖。
102. 任务应有负责人、截止时间、状态、证据/备注和超时策略；服务层把状态更新与待通知记录一起提交，由异步投递完成闭环。
103. 联系医生先根据患者授权关系过滤候选目标，再校验发送方范围与通知内容最小化。不能接受用户直接传入任意医生 ID 后就发送病历。
104. token 使用安全随机值，经 HTTPS 传输，数据库只保存哈希和元数据；设置过期、撤销、设备/会话绑定并只在创建时展示明文。日志禁止记录 token。
105. 查看、搜索、导出、修改、授权、审批、告警确认和通知都要审计。日志需追加式、访问受限并包含 actor、对象、动作、结果、时间与关联 ID。
106. 应答应保持非诊断性：提示立即联系急救服务、家属或医护，不等待聊天结果；后台将消息作为高优先事件，按已授权链路通知并记录，但不得声称系统已完成救援。
107. 最小要求是传输 TLS、敏感字段/令牌加密、日志脱敏、分权密钥管理、加密备份和轮换流程。当前本地实现与生产密钥系统之间要如实区分。
108. 删除请求需要区分可删除的应用数据、法定/审计留存数据和备份。应以软删除/去标识化与保留策略记录处理结果，而非直接物理删除所有痕迹。
109. 权限测试应覆盖角色、患者关系、过期授权、资源枚举、并发审核、通知收件人和审计完整性；最好用集成测试验证真实 HTTP 与数据库边界。

## 10. 小红书舆情、Sidecar 与控制台（110-120）

110. Python Sidecar 可隔离采集依赖、Cookie 和不稳定运行时，避免爬取崩溃影响主 JVM；主服务保留鉴权、任务状态和业务决策。它也让采集替换不牵动核心服务。
111. 主服务创建项目和关键词，提交 Sidecar 任务并持久化 job；结果规范化、去重和入库后进入语义分析/评分，达到阈值生成事件和告警，最后可生成日报与投递。每一步都应有显式状态。
112. 契约应定义请求、externalJobId、状态枚举、分页结果和错误码；主服务按 jobId 轮询/接收结果并以幂等导入保护重试。超时不等于失败结果，应保留“未知/待重试”状态。
113. `AUTH_EXPIRED` 要提示重新授权，`SIDECAR_RESTARTED` 可重查/重提可重入任务，部分关键词失败要在报表中注明范围。绝不能把部分数据标成完整采集。
114. HMAC 比普通 hash 更难被字典反查，且可稳定关联同一作者；密钥轮换会改变新 key 下标识，需存 key version 或制定历史迁移策略。不同项目是否可关联取决于隐私设计。
115. 外链访问要校验允许域名/格式，并让控制台按项目授权后再展示。用户生成 URL 不应直接作为跳转目标，防开放重定向和恶意站点。
116. 风险评分是排序辅助，应由情绪、传播、时效、置信等可解释信号组成；它不等于事实、法律结论或公关结论。高风险事件必须保留原文证据与人工复核。
117. 事件状态由受控转换矩阵限制，例如待处理、确认、处理中、解决、误报；每次转换记录操作者、原因和版本，防止无权限或并发覆盖。
118. 订阅按项目/阈值/渠道保存，投递前再次校验权限；每次投递有幂等键、尝试次数和失败原因。目标失效或邮件失败应有限次重试和可见告警。
119. 控制台必须认证用户并按项目成员/管理员授权；所有详情、下载、事件和订阅端点用服务端 project scope 过滤，不能信任前端传来的 projectKey。
120. 采集内容可能有 XSS、隐私与版权风险，展示时转义/消毒，导出和日志做最小化与权限控制，并制定数据保留与来源合规规则。

## 11. 定时报表、通知与文件存储（121-127）

121. 报表计划应保存项目、名称、频率、用户时区、本地执行时间、格式和接收方；服务端算出下一次 UTC 执行点。周/月边界必须通过固定时钟测试。
122. 多实例调度需用数据库条件更新/租约抢占，把计划锁定为运行中，再创建唯一运行记录。调度锁防重复启动，运行记录防重复执行，二者不可互相替代。
123. 采集、分析、生成、存储、投递分别记录状态；可重入读/分析可有限重试，文件和投递使用运行 ID 幂等。部分完成的报告应明确标注数据范围和失败项。
124. 先把文件写到临时 key，校验后以受控 key 发布，并在事务中记录元数据；提交失败则清理文件，文件失败则不标记可下载。后台清理孤儿文件和孤儿元数据。
125. 下载接口验证登录与项目授权，使用短期签名/受控流式下载并限制频率。清理任务按过期和引用状态删除，删除前可标记为待删除防并发下载。
126. 负面帖通知以订阅 ID+帖子 ID+规则/版本为幂等维度，记录是否已投递。规则变更需决定是新规则重新通知还是仅影响未来数据，并在产品层说明。
127. 失败要记录结构化原因、可重试性和下一次时间；超过最大次数进入待人工处理。用户界面提供运行/投递状态，不能只在服务器日志中可见。

## 12. 数据库、迁移、事务与测试（128-137）

128. 迁移按领域演进是合理的，但跨领域外键和共享表应最少；命名、版本和所有权要清晰。数据库不是所有业务规则的替代，关键状态转换仍在服务层校验。
129. 已发布迁移绝不能简单删除/改号；老库的 Flyway history 已记录旧版本。安全方案是恢复原迁移或用新的兼容迁移向前演进，先在生产副本验证 checksum/history，再发布，绝不手改线上历史掩盖问题。
130. 计划、任务、提醒、支付、事件、告警和报表运行都有竞争更新，应使用 version 或状态条件更新。对“只能领一次”的任务，状态条件通常比读后写更直接。
131. 同一 MySQL 中创建业务记录和 outbox、计划和任务、任务状态和通知记录必须在同一 `@Transactional`。模型、微信、邮件和文件不能放在长事务里，应事务后异步执行。
132. JDBC 必须使用参数化 SQL、关闭资源/由模板管理资源、为批量操作检查每条结果，并对热点查询做执行计划和索引验证。N+1 通过批量查询或 join/聚合显式消除。
133. 索引围绕访问模式：会话按会话+时间，提醒按状态+到期时间，告警/报表按状态+下次运行，舆情按项目+时间/风险。用 `EXPLAIN`、慢查询和真实数据量验证，而不是只凭字段直觉。
134. 跨 MySQL、Qdrant、文件与外部 API 不应强上 2PC，因为可用性和实现代价很高。使用本地事务记录意图、幂等外部动作、补偿与对账任务获得最终一致性。
135. 单测验证纯逻辑，集成测 repository/事务/HTTP 契约，端到端测关键用户链路；当前最缺的往往是真实微信、模型、邮件和 Sidecar 故障注入。应明确哪些测试需要沙箱账户。
136. 模型测试固定 schema 和模拟响应，使用 golden set 回归工具选择/RAG 回答，记录版本和阈值。不要断言自由文本完全一致，应断言结构、引用、禁止行为和关键事实。
137. 编码与 classpath 问题常只在 CI、Windows/Linux 或打包 jar 暴露。测试它们能防止文档/中文消息乱码、资源找不到等部署差异。

## 13. 安全、可观测性与运维（138-147）

138. 密钥应由环境或专用 secret manager 注入，按服务账号最小权限分发并可轮换；禁止放入 Git、数据库明文、日志、异常响应或报告。开发 `.env` 只是本地便利，不是生产方案。
139. `SecretMasker` 可减少已知格式在日志中的泄露，但无法替代不记录敏感原文、访问控制和代码审查。泄露后应立即撤销凭据、检索日志/备份范围、轮换并补检测规则。
140. 用户输入和网页/文档内容都是不可信数据；输出 HTML 在渲染层转义/消毒，文件名/URL 在边界校验，邮件与报告不执行嵌入脚本。模型输出也不天然安全。
141. Prompt Injection 靠数据/指令隔离和工具权限控制；SSRF 靠 URL allowlist 和网络出口限制；路径遍历靠 canonical path/root 校验；下载和重定向靠服务端授权与目标白名单。
142. 连续 429 时做有上限的指数退避、熔断和任务排队/降级，并向用户显示处理中或稍后重试。必须同时限制入口，防止重试把队列和成本拖垮。
143. 每个 client 要有连接/读取 deadline、可重试错误白名单、抖动退避、并发隔离和熔断。重试会在下游过载时放大流量，因此只针对幂等且短暂故障。
144. 在入口生成 request/trace ID，并在日志/MDC、业务记录、outbox、工具调用和 Sidecar header 透传；用户标识采用内部 ID 或脱敏摘要。这样才能从一次用户消息追到最终投递。
145. 监控包括 JVM/线程池、DB/Qdrant、模型/工具/Sidecar 延迟和错误、队列、提醒/报表投递、权限拒绝与敏感操作。告警要以 SLO 和趋势触发，而非仅 CPU 阈值。
146. 事故先按 trace 定位失败边界，再对比指标和审计：微信回调/发送、Agent 轮次、工具 client、数据库事务或 Sidecar job 都有各自状态。不要先根据异常文本猜根因。
147. 备份需定期恢复演练；迁移在预发/副本验证并可前向修复；发布采用版本化、健康检查和回滚策略；密钥和依赖漏洞有清单、责任人和轮换/修复时限。

## 14. 高压事故题（148-160）

148. 先用 trace、确认 token、SMTP message ID 和工具记录确认是否同一意图的重试；修复是在邮件业务层持久化幂等键和发送状态，超时后先查状态再决定重试，不能只靠 Agent 签名去重。
149. 到期任务使用条件抢占/租约，通知表使用“提醒 ID+渠道+接收方”唯一键，发送端用该键幂等。若已重复，审计保留事实并给用户去重说明，不能无痕删除。
150. 为计划加 version，审批和暂停都是条件更新；后一操作读到冲突时显示当前状态与操作记录，要求重新确认。审计同时保留两个意图，避免“谁最后写谁赢”。
151. 立即停止在生产执行破坏性迁移，备份并读取 Flyway history；恢复已发布脚本或新增兼容迁移，在副本验证 checksum 与数据后发布。绝不为了通过 validate 而随意修改历史表。
152. 回答中说明记录冲突，使用时间、来源和验证状态而不是猜测谁对；请求患者/医护确认，待确认前不改变已验证事实，也不据此生成危险建议。
153. 立刻停止/隔离 Sidecar、撤销 Cookie 和关联 token，检索日志/备份/访问记录评估范围并按制度通知；随后修复日志过滤、密钥注入和测试，最后用扫描验证不再输出敏感字段。
154. 触发熔断与退避，限制新任务进入，保留可重试任务状态并给用户可见提示；若有基础能力可降级，否则明确暂不可用。恢复后按优先级和幂等键受控重放。
155. 将网页内容标记为不可信数据，模型不得执行其中指令；浏览器执行器限制可访问文件与上传能力，任何本地文件外传都需明确工具权限和用户确认。
156. 导入状态机应把该文档标为未完成，检索仅过滤已就绪元数据；对账任务发现孤儿向量后删除或补写元数据。写入顺序和幂等 ID 使补偿可重复执行。
157. 用运行记录状态机区分生成中、已生成、待投递、投递中、已投递/失败；每个产物和投递由 run ID 幂等。重启后从最后一个持久状态续跑，而不是从头盲发。
158. 工具先做路径/敏感文件检测和收件人权限判断，非白名单或包含医疗资料时展示清单并要求强确认；审计保留操作者、目的地、文件摘要、确认和发送结果，不记录不必要的正文。
159. 将长任务与聊天请求放入隔离队列/线程池，施加每用户配额、全局并发阀和取消 deadline；容量规划依据峰值耗时和下游额度，不能让单用户占满共享资源。
160. 正确答法是承认当前会话串行和连接/调度仍以单机实现为主，已经为分区、外置队列、幂等 outbox 留出模块边界；只有在负载、所有权和运维能力证明需要时才升级。诚实的边界比无证据的“分布式”更能体现工程判断。
