# 患者照护协同 Agent 功能方案

## 1. 文档目标

本文档定义一个面向患者、家属、医生、护士、康复师和营养师的患者照护协同 Agent。Agent 负责记录患者日常信息、执行照护计划、协调参与者、发现风险、主动提醒并生成趋势报告。

阿尔茨海默病患者照护是该 Agent 的一个应用场景，但系统能力不局限于单一病种，还可以扩展到：

- 认知障碍与老年照护；
- 术后康复；
- 糖尿病、高血压等慢病管理；
- 骨折、关节置换等运动康复；
- 肿瘤治疗后的居家随访；
- 吞咽障碍和营养风险管理；
- 长期服药与复诊管理；
- 出院后的家庭照护协同。

本系统定位为照护辅助、信息记录和风险提醒工具，不替代医生诊断、处方、康复评估或紧急医疗服务。

## 2. 产品定位

Agent 围绕一个长期的患者照护档案工作，而不是只完成一次问答。

完整业务闭环为：

```text
建立患者档案
→ 绑定患者、家属和医护人员
→ 录入并审核照护计划
→ 每日推送任务
→ 收集文字、语音、图片和设备数据
→ 形成结构化记录
→ 执行确定性安全规则
→ 通知相关照护人员
→ 跟踪处理结果
→ 生成日报、周报和阶段报告
```

## 3. 使用角色

| 角色 | 主要能力 |
| --- | --- |
| 患者 | 记录事情、完成签到、查看任务、查询已经确认的信息、反馈不适 |
| 家属/照护人 | 查看授权范围内的状态、确认记录、处理告警、补充观察 |
| 医生 | 查看趋势摘要、审核医嘱相关计划、接收需要专业处理的异常 |
| 护士 | 管理随访任务、查看执行情况、补充护理观察 |
| 康复师 | 创建和审核康复动作、设置禁忌和阶段目标 |
| 营养师 | 设置营养目标、饮食限制和可替换方案 |
| 系统管理员 | 管理账号、权限、审计、配置和服务状态，不读取无权限的病历内容 |

## 4. 核心功能

### 4.1 患者档案

- 保存基础身份、联系方式、时区和主要照护人；
- 记录疾病、手术、过敏、行动能力和沟通偏好；
- 保存医生确认的饮食限制、康复限制和照护目标；
- 区分患者自述、家属观察、设备数据和医护记录；
- 支持档案版本、修改历史和数据来源追踪；
- 支持患者或监护人导出、更正和删除数据。

### 4.2 生活与记忆记录

患者可以通过文字、语音、图片或文件记录想要保存的事情，例如人物、地点、日程、生活事件和重要约定。

处理流程：

```text
保存原始内容
→ 语音转写或图片识别
→ 提取人物、时间、地点和事件
→ 检查冲突及缺失字段
→ 请求患者或家属确认
→ 保存为可信记录
```

功能要求：

- 保留原始证据和结构化结果；
- 使用 `RECEIVED`、`EXTRACTED`、`WAITING_CONFIRMATION`、`VERIFIED`、`CORRECTED`、`REJECTED` 状态；
- 查询时优先返回已确认记录；
- 展示记录时间、记录人和来源；
- 不允许模型补充记录中不存在的患者经历；
- 支持按人物、日期、地点、事件类型和关键词检索；
- 支持设置记录的共享范围。

### 4.3 每日状态签到

Agent 根据照护计划定时发起简短签到，问题可以按病种和康复阶段配置。

通用签到项目包括：

- 睡眠；
- 饮食和饮水；
- 情绪；
- 活动情况；
- 疼痛或其他不适；
- 服药是否已确认；
- 是否发生跌倒、迷路或其他意外；
- 患者自由描述；
- 家属补充观察。

签到结果转换为结构化指标，并保留原始回答。Agent 分析患者相对于个人基线的变化，不使用简单的人群平均值直接判断病情。

### 4.4 照护计划

系统支持以下计划：

- 服药确认计划；
- 饮食与饮水计划；
- 康复训练计划；
- 认知训练和生活活动计划；
- 睡眠与作息计划；
- 检查、复诊和随访计划；
- 家属陪护和轮班计划。

计划状态为：

```text
DRAFT → WAITING_REVIEW → APPROVED → ACTIVE → PAUSED → COMPLETED
```

涉及医学判断的计划必须由相应专业人员审核。Agent 不得自行改变处方、药量、训练禁忌或临床营养要求。

### 4.5 任务与主动提醒

- 创建一次性、每日、每周和自定义重复任务；
- 提醒患者完成签到、服药确认、饮食记录、康复训练和复诊；
- 支持完成、延后、取消和重新安排；
- 记录每次发送及响应结果；
- 发送失败时重试；
- 使用幂等键避免重复通知；
- 长时间未响应时按预设联系人顺序升级。

项目现有的提醒调度、数据库抢占、失败重试和主动消息发送能力可以直接复用。

### 4.6 安全监控

第一阶段支持基于消息、签到和人工记录的安全监控：

- 超过约定时间未签到；
- 连续未进食、未饮水或未完成照护任务；
- 患者表达迷路、不知道所在位置或无法联系家人；
- 患者或家属报告跌倒；
- 重复服药风险；
- 夜间异常求助；
- 疼痛、呼吸困难等预设紧急关键词；
- 与个人基线相比出现持续明显变化。

定位、跌倒自动识别和生命体征监测需要患者明确授权，并接入手机、定位卡、智能手表或经过验证的医疗设备。仅依靠微信聊天不能可靠实现这些能力。

告警分级：

| 等级 | 用途 | 默认动作 |
| --- | --- | --- |
| `INFO` | 一般提醒 | 提醒患者或记录事件 |
| `ATTENTION` | 需要家属关注 | 通知主要照护人并等待确认 |
| `URGENT` | 明确的高风险事件 | 优先通知家属，提示联系专业人员或急救服务 |

告警状态：

```text
OPEN → ACKNOWLEDGED → RESOLVED
                    → ESCALATED
                    → FALSE_ALARM
```

高风险告警必须由确定性规则触发或经过人工确认。大模型识别出的模糊信号只能进入待确认状态。

### 4.7 家属协同

- 一个患者可绑定多个照护人；
- 设置主要照护人、备用联系人和通知顺序；
- 管理家属可查看的数据范围；
- 家属可以补充生活观察和处理记录；
- 支持家属确认、误报标记和告警关闭；
- 支持生成家庭照护排班和待办汇总；
- 避免把每条患者消息都转发给所有家属。

### 4.8 医护协同

- 医护人员只查看患者授权且与照护相关的数据；
- 提供结构化趋势摘要，而不是大量原始聊天记录；
- 支持审核饮食、康复和随访计划；
- 支持对异常添加专业意见；
- 支持生成复诊材料和随访报告；
- 支持记录报告是否已被查看和处理。

### 4.9 日报、周报和趋势报告

报告可以包含：

- 签到和任务完成率；
- 睡眠、饮食、饮水、情绪和活动趋势；
- 不适、跌倒、迷路等事件；
- 家属观察；
- 告警数量、等级和处理时长；
- 当前照护计划执行情况；
- 需要专业人员关注的问题；
- 原始数据和事件引用。

报告不得自动生成确诊结论，也不得声称患者病情改善或恶化，除非该结论来自经过授权的专业人员。

### 4.10 多渠道通知

通知层使用统一接口：

```text
NotificationChannel
├─ WechatChannel
├─ WeComChannel
├─ SmsChannel
├─ EmailChannel
└─ AppPushChannel
```

个人微信机器人存在稳定性和账号风险。正式医疗照护场景优先使用企业微信、医院已有随访系统、短信或具备官方授权的渠道。

## 5. 病种与场景扩展

通用能力由核心系统提供，具体场景通过规则包和模板扩展。

| 场景 | 可扩展能力 |
| --- | --- |
| 阿尔茨海默病和认知障碍 | 可信记忆、日常定向信息、走失风险、照护人协同 |
| 术后康复 | 伤口观察、疼痛记录、康复任务、复诊提醒 |
| 糖尿病 | 饮食执行、血糖数据接入、用药确认、异常上报 |
| 高血压 | 血压数据接入、测量提醒、生活方式记录 |
| 骨科康复 | 动作计划、训练记录、负重限制、疼痛变化 |
| 肿瘤院后随访 | 症状记录、营养状态、治疗周期和复查提醒 |
| 老年综合照护 | 跌倒、营养、睡眠、活动和多照护人协同 |

每个规则包必须注明适用人群、数据要求、版本、医学来源、审核人员和生效时间。

## 6. 微信工具设计

建议拆分以下 Function Calling 工具：

```text
care_profile_manage       管理患者档案
care_team_manage          管理照护关系和权限
care_memory_record        记录生活事件
care_memory_search        查询可信记录
care_memory_correct       修正错误记录
care_checkin_submit       提交每日状态
care_plan_manage          管理照护计划
care_task_list            查询当日任务
care_observation_record   家属或医护补充观察
care_status_query         查询近期趋势
care_alert_list           查询告警
care_alert_ack            确认和处理告警
care_report_generate      生成日报或周报
```

工具类保持轻量，只负责参数读取、调用 Service 和返回 `WechatReply`。权限、医学规则、状态流转、通知策略和报告生成均放在领域服务中。

## 8. 多线程和异步处理

建议创建独立的有界线程池：

```text
care-media             语音转写、OCR 和媒体处理
care-extraction        结构化提取和摘要
care-notification      家属及医护通知
care-report            日报、周报和阶段报告
```

处理原则：

- 原始事件必须先持久化，再异步处理；
- 不同患者可以并行；
- 同一患者的状态变更按照事件序号顺序提交；
- 安全规则优先于耗时的模型摘要；
- 告警通知与普通报告使用不同线程池；
- 队列必须有容量上限、超时和拒绝策略；
- 使用 Outbox 保证数据库事务与通知投递最终一致；
- 所有任务具备幂等键，程序重启后可以恢复。

## 10. 医疗安全边界

Agent 可以：

- 记录和整理患者信息；
- 按已审核计划提醒患者；
- 统计完成情况和变化趋势；
- 根据确定性规则提示风险；
- 帮助家属和医护人员协同；
- 生成带来源的摘要和报告。

Agent 不可以：

- 独立诊断疾病；
- 修改药物、剂量或治疗方案；
- 自由生成未经审核的康复动作；
- 用模型输出替代急救判断；
- 编造患者记忆或病历；
- 未经授权持续获取位置或设备数据；
- 在未确认的情况下对外发送完整病历。

## 11. 隐私与合规要求

- 对健康、身份、位置和家庭关系数据取得单独、明确授权；
- 只收集完成照护所必需的数据；
- 传输使用 HTTPS，数据库和媒体文件加密存储；
- 使用基于角色和患者关系的数据权限；
- 记录查看、导出、修改、分享和删除行为；
- 日志中隐藏姓名、电话、地址、证件号和病历内容；
- 支持授权撤销、数据导出、更正和删除；
- 为原始语音、图片和报告设置保存期限；
- 正式上线前完成隐私、威胁模型和医疗合规评审。

## 12. 医疗知识与 Skill

通用 Skill 可以用于语音转写、文件处理、报告生成和安全审查，但不能替代医疗规则。

建议创建项目专用 Skill：

```text
patient-care-assistant/
├─ SKILL.md
├─ references/
│  ├─ scope-and-boundaries.md
│  ├─ clinician-approved-checkins.md
│  ├─ escalation-policy.md
│  ├─ report-template.md
│  └─ scenario-index.md
└─ scripts/
   └─ validate-care-plan.*
```

Skill 负责对话方式、信息追问、工具选择、禁止行为和报告格式。临床阈值、权限、告警状态和数据校验必须由 Java 服务、数据库和经过审核的规则配置实现。

## 13. 分阶段交付

### 第一阶段：基础闭环

- 患者与照护关系绑定；
- 授权和角色权限；
- 生活事件记录、确认和查询；
- 每日签到；
- 定时提醒；
- 未签到、跌倒和迷路等基础规则；
- 家属告警确认；
- 每周趋势报告；
- 审计日志。

### 第二阶段：专业照护计划

- 医护人员审核流程；
- 饮食、康复和随访计划；
- 患者个人基线；
- 病种和场景规则包；
- 多级告警升级；
- 企业微信、短信和邮件渠道。

### 第三阶段：设备与医院系统

- 智能手表、定位设备和家庭传感器；
- 医院 HIS、EMR 或随访平台授权接口；
- HL7/FHIR 数据适配；
- 多机构和多租户隔离；
- 经过验证的临床量表与规则。

## 14. 第一版验收标准

- 原始记录不会因模型提取失败而丢失；
- 未确认的信息不会被当作可信记忆返回；
- 同一事件重复提交不会生成重复记录和通知；
- 同一患者的状态更新不会因并发发生乱序覆盖；
- 高等级告警不被普通报告任务阻塞；
- 家属可以确认、升级、关闭和标记误报；
- 医护报告中的每个关键结论可以追溯到原始记录；
- 不输出诊断、处方和未经审核的康复方案；
- 所有敏感数据访问都有权限校验和审计记录；
- 微信或外部服务不可用时，事件可以恢复和重试。

## 15. 建议的首个落地版本

第一版建议定位为“患者居家照护记录与家属协同 Agent”，先覆盖通用功能，同时选择一个场景做深度验证。

建议首个完整闭环：

```text
患者记录事情
→ 家属确认
→ 每日状态签到
→ Agent 执行安全规则
→ 异常通知家属
→ 家属处理并关闭告警
→ 每周生成照护趋势报告
```

该闭环可以同时用于认知障碍、术后康复、慢病管理和老年综合照护，后续通过规则包扩展，不需要重写核心系统。
